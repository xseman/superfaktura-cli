# 002 · CLI

`internal/commands`. One file per resource, all the same shape.

## Adding a command

```
  invoice.go
  ├── var invoiceColumns = []render.Column{…}   ← the table, also used by the TUI
  ├── var invoiceFields  = []render.Field{…}    ← the detail view
  │
  ├── list    → listOptions.bind(cmd)   paging, sort, search, --filter
  │             fetchList(…)            →  emitList(…)
  │
  ├── write   → readPayload(--data)     start from a raw document if given
  │             put(doc,"Invoice",…)    layer flags on top
  │             requirePayload(doc)     refuse an empty write
  │             emitWrite(raw,"Invoice","Invoice created")
  │
  └── download→ api.Download(…)         →  writeBinary(…)   honours -o -
```

**Never print directly.** `emit(data, table)` renders the table for humans and
the envelope for everything else, so `--json`, `--quiet`, `--ids-only`,
`--count` and `--jq` keep working for free.

**Name the model at the call site.** `emitWrite(raw, "Invoice", …)` — an earlier
version guessed it alphabetically and every invoice create reported its
*client's* ID.

## Output contract

**One invocation emits exactly one document.**

```
   RunE returns
        │
        ├── nil ──────────────► already emitted, exit 0
        │
        ├── *output.Error ────► envelope + ExitCodeFor(Code)
        │
        ├── reported{err} ────► exit code only, nothing printed
        │                       (the command already emitted; used by
        │                        `sf auth status` and `sf doctor` reporting
        │                        a failed check)
        │
        ├── *client.Planned ──► render the plan, exit 0        (--dry-run)
        │
        └── other (cobra) ────► usage error, exit 1
```

### What to do next

A write says what happened and stops, leaving the user to work out what the
record is called and which command touches it next — both of which the command
that just ran knows.

```console
$ sf invoice create --client 83559 --item 'Consulting:2:500:23'
Invoice created
ID: 311525

Next:
  sf invoice view 311525               see it
  sf invoice pdf 311525                download the PDF
  sf invoice send 311525 --to <email>  email it to the client
```

`emitWrite` takes them as trailing `output.Step` values whose `Cmd` carries a
`%s` for the new id, which the server has not answered with yet at the call
site. They ride the envelope as `next` for machines and print as the block
above for people.

That second half needed a fix in `emit`: the human branch returned before it
looked at its options, so anything carried there reached `--json` and nobody
else.

**`--jq` does not see them**, and that is deliberate rather than a gap. It
filters the *data*, so a script writes `.[0].Invoice.id` instead of
`.data[0]…` — which also means `summary`, `meta` and `next` are invisible to a
filter. Ask for `--json` to read them.

**Machine output preserves the API's key order.** A response travels to
`--json` and `--quiet` as the bytes the API sent — `NormalizeData` passes raw
JSON through verbatim, `listResult.Raw` carries each row's original bytes next
to the maps that drive tables and filters, and the detail and write paths emit
the response they received. The maps exist for rendering and lookup only; the
moment one is re-marshaled into output, Go re-sorts every object's keys and a
consumer diffing two runs drowns in reshuffles that changed nothing. Rows the
CLI synthesizes rather than receives (the keyed fallback injects ids) carry no
raw bytes and fall back to sorted maps, which at least never move between
runs. Pinned by `TestRawDataKeepsKeyOrder` and `TestDecodeListKeepsRawAligned`.

The comment above `emit` used to promise that "exit codes, breadcrumbs and
`--jq` behave identically everywhere". There were no breadcrumbs, the human
branch never looked at its options, and `--jq` has never gone through the
envelope at all — one sentence, three claims, none of them true. It now
describes what the function does.

| Exit | Code            | Meaning                         |
| ---: | --------------- | ------------------------------- |
|    0 | —               | success                         |
|    1 | `usage`         | bad arguments or flags          |
|    2 | `not_found`     | no such resource                |
|    3 | `auth_required` | not authenticated               |
|    4 | `forbidden`     | authenticated but not permitted |
|    5 | `rate_limit`    | quota exhausted                 |
|    6 | `network`       | connection, DNS or timeout      |
|    7 | `api_error`     | the server reported a failure   |
|    8 | `ambiguous`     | more than one match             |

An unknown code maps to 7 — assuming a server-side failure is the safest
default. `usageErrorf` is the shorthand for the common case.

## Resolving names

`resolve.go` turns a name into an identifier for `--client` and `--tag`. A
numeric value passes through untouched; anything else costs a lookup.

```
  --client "Acme s.r.o."
        │
        ├─ numeric? ──────────────────────► use as-is, no request
        │
        ▼  fetch candidates
  ┌──────────────────────────────────┐
  │ exactly one match                │──► use it
  │ several, one exact               │──► the exact one wins
  │ several, none exact              │──► exit 8, candidates in Error.Matches
  │ none                             │──► exit 2
  └──────────────────────────────────┘
```

Two rules are deliberate:

- **An exact match beats a longer one**, or "Acme s.r.o." could never be
  selected while "Acme s.r.o. Trading" exists.
- **Several matches fail** rather than picking one. A wrong guess puts an
  invoice on another company's account.

Tag names are not a convenience: the API accepts only numeric IDs and silently
drops names, so an unresolved tag name looks like success and saves nothing.

## Create and edit share one flag set

`invoiceWriteFlags` and `expenseWriteFlags` are bound by both commands of their
pair, because the two drifted apart when they were declared separately: invoice
create could set a client and a type that edit could never correct, and edit an
issue date that create could not — so a back-dated invoice had to be made today
and then edited.

Only flags that mean nothing after the fact belong to one side:
`--checksum` recovers a create response and `--new-client` names a client that
does not exist yet.

`--item` is the third, and for a different reason. `/invoices/edit` **appends**
line items rather than replacing them — measured, see
API-DISCREPANCIES §B7 — so a flag reading "these are
the items" would duplicate an invoice's contents. The append is offered under
the name it deserves instead:

```sh
sf invoice item list   --invoice 309101
sf invoice item add    --invoice 309101 --item 'Consulting:2:500:23'
sf invoice item delete 804905 --invoice 309101
```

Both `delete` forms take ids as arguments, so `--ids-only` pipes into either:

```sh
sf --ids-only invoice item list --invoice 309101 | xargs -n1 sf invoice item delete --invoice 309101
```

`item list` costs the one request that fetches the document — the items travel
inside it, so there is nothing else to ask for. It exists because `item delete`
takes an **item** id, and reading one out of `--jq` was the only way to get it.
`--ids-only` prints exactly those ids, so the two commands chain.

`TestCreateAndEditOfferTheSameFields` fails on any other one-sided flag, and
names `creationOnly` as the place to record a deliberate exception.

## Flags

The documented filter sets run to twenty-odd parameters per resource and grow
with the API. Promoting each to a flag would bury the useful ones, so the common
filters get flags and `--filter key=value` passes through the rest.

`per_page` ceilings differ by resource — 200 for invoices, 100 for expenses —
and are enforced client-side so a doomed request is never sent.

## The command surface is pinned

`SURFACE.txt` is a snapshot of the whole tree: every command, flag and
positional argument. It is untracked — `make surface-snapshot` writes it, and
the test diffs against it while it exists, so an intentional change is read,
not merely committed.

```sh
make surface-snapshot   # write or refresh the local snapshot
```

## Record detail

`sf <resource> view` and the browser's detail pane render through the same
`render.Renderer` — they already print the same values, and letting them diverge
in shape is the drift the shared column list exists to prevent.

Most resources use `render.Pairs`: an optional headline over two columns of
label/value. A **document is not a bag of fields**, so invoices and expenses
compose their own from the same primitives:

```
 2026001  ·  Acme s.r.o.                          787.20 EUR   ← Headline
 regular  ·  due 2026-09-15  ·  paid 2026-08-01       UNPAID
 ─────────────────────────────────────────────────────────────
 QTY  ITEM          UNIT  VAT   TOTAL                          ← render.Rows
   8  Konzultácie  75.00  23%  738.00                            over InvoiceItem
   1  Cestovné     40.00  23%   49.20
 ─────────────────────────────────────────────────────────────
 PAYMENTS                         Net     640.00               ← SideBySide(
 2026-08-01  transfer  152.80     VAT     147.20                   Rows(payments),
                                  Total   787.20                   Values(totals))
                                  Paid    300.00
                                  To pay  487.20
 ─────────────────────────────────────────────────────────────
 Variable 20260801  ·  ID 309101                               ← render.Inline
```

**The items and payments cost nothing.** A list row is a complete record, so
they were in hand all along — the field list that came before described an
invoice without ever showing one.

| Primitive         | Does                                                         |
| ----------------- | ------------------------------------------------------------ |
| `Pairs`           | the default renderer: headline over two columns              |
| `Rows`            | tabulates a repeated sub-record; nothing when there are none |
| `Values`          | label/value pairs, `Field.Right` stacking decimal points     |
| `SideBySide`      | two blocks at a fixed gutter                                 |
| `Inline`          | `Variable X · ID Y` on one line                              |
| `Rule`, `Caption` | a divider, a section heading                                 |

Rules that keep it readable, each of them a defect that was there first:

- **Amounts are right-aligned** (`Field.Right`, `Column.Right`). A column of
  money whose decimal points do not stack is not scannable, which for an
  accounting tool is most of the problem.
- **Empty blocks are skipped.** No items, no payments — no headings for them.
- **An unnamed rate line is not tabulated.** SuperFaktura writes an expense's
  amount as one nameless item, and a table of a single blank row restating the
  total below it is noise. A *named* expense item still gets its table.
- **A header row of empty column names is dropped**, so payments read as
  `2026-08-01 transfer 152.80` without a blank line above them.

**The badge is derived, not read.** `Invoice.status` only counts up to
"partially paid" — overdue is a fact about today, not about the record — so
`documentStatus` computes it from what is outstanding and when it was due, the
same rule the overview counts by.

`Tone` travels with the headline so the browser can colour it (green paid,
amber unpaid, red overdue) without `render` knowing about lipgloss. `--json` is
unaffected: this is the human-facing table only.
