# 003 · TUI

`sf ui`. A browser for the account, on Bubble Tea.

`internal/tui` knows about tables and keystrokes and has no idea what
SuperFaktura is. It also owns `FormTheme`, which is exported because the
browser is not the only place huh runs — `auth login`, `client create` and
`invoice create` prompt from the CLI, and on the stock theme they came out
fuchsia, looking like a different application. `commands/ui.go` supplies the resources, columns, fields and
actions — the same values the CLI prints, so the two views cannot drift.

## Why it exists

A list row is a complete record, so the detail pane costs **no request**.
Browsing 20 invoices is 1 request here against 21 in a naive
list-then-fetch design. See [000 · Architecture](000-architecture.md).

## Layout

The view must come to **exactly** the terminal height. One line too many and the
frame scrolls, which silently detaches the detail pane from the highlighted row
— it looks like a data bug and is a layout bug.

```
 ┌────────────────────────────────────────────────────────────┐ ┐
 │ Overview  Invoices  Clients  Expenses           876/1000   │ │ headerLines 2
 │                                                            │ ┘  tabs + quota
 │ filter: Unpaid  period: This year  fetched just now         │ ┐ filterLines 2
 │                                                            │ ┘
 │ ID      NUMBER   CLIENT          ISSUED      TOTAL         │ ┐
 │────────────────────────────────────────────────────────────│ │
 │ 309127  2026006  Acme s.r.o.     2026-08-01  1.23          │ │ listHeight()
 │▓309128▓▓2026007▓▓Beta a.s.▓▓▓▓▓▓▓2026-08-02▓▓99.00▓▓▓▓▓▓▓▓▓▓│ │  = height
 │ 309129  2026008  Gamma s.r.o.    2026-08-02  4.50          │ │  − header
 │                                                            │ ┘  − filter
 │──────────────────────────────────────────────  enter expand│ ┐  − footer
 │   Number       2026007                                     │ │ detailHeight()
 │   Client       Beta a.s.                                   │ ┘  = height/3,
 │                                                            │ ┐    4..14
 │ page 1 of 1 · 6 records                                    │ │ footerLines 3
 │ ↑/↓ navigate · / filter · enter expand · r refresh · q quit│ ┘
 └────────────────────────────────────────────────────────────┘
```

`detailHeight` depends only on the terminal, never on how many fields the
current resource has — a height that changed with the tab made the whole layout
jump on every switch.

The frame this draws is pinned by a golden file, down to which cells are
inverted. Changing anything below means regenerating it — see
[006 · Testing](006-testing.md).

The selected row is **inverted, not framed**. Framing it with rules above and
below made it three lines tall, so every row beneath shifted on each keypress
and the list appeared to jump. The row is padded to full width *before* styling,
or the bar stops where the text does.

The list is rendered in `list.go` rather than by `bubbles/table`, which removed
two bugs that table had already caused: a column count that had to match rows
from the previous resource, and a cursor that starts at -1.

## The message loop

```
   keystroke ──┐
               ▼
        ┌─────────────┐   mode == modeForm?   ┌──────────────┐
        │  Update()   ├──────── yes ─────────►│ updateForm() │
        └──────┬──────┘                       └──────────────┘
               │ no                            huh takes EVERY message,
               ▼                               not only keys — anything
     ┌──────────────────┐                      left to fall through
     │ tab / f / n / r  │  issues a load       reaches the table and the
     │ ↑ ↓ / enter      │  free, local         form sits on field one
     │ action key       │  may write
     └────────┬─────────┘
              ▼
        ┌──────────┐   cached?   ┌───────────────────────────┐
        │  load()  ├────yes─────►│ loadedMsg{cachedAt: …}    │
        └────┬─────┘             └───────────────────────────┘
             │ no
             ▼
     ┌───────────────┐  goroutine   ┌────────────────────────┐
     │ Resource.Load ├─────────────►│ loadedMsg{resource,    │
     └───────────────┘              │           page, scope} │
                                    └───────────┬────────────┘
                                                ▼
                                    ┌────────────────────────┐
                                    │ stale(msg)? → drop it  │
                                    └────────────────────────┘
```

**A response says which request it answers.** Walking the tabs faster than the
network answers otherwise puts one resource's rows under another's columns:

```
   t0  press tab → Invoices     request A ──────────────┐
   t1  press tab → Clients      request B ────┐         │
   t2                                         ▼         │
       B lands, matches → shown                         │
   t3                                                   ▼
       A lands, resource=0 ≠ 1 → DROPPED
       (without the guard: invoice rows under client
        columns — every cell blank, under a record
        count matching nothing on screen)
```

## Load invariants

- **Nothing polls.** Only `r`, a tab switch or a page change fetches. The model
  tests count loads for exactly this reason.
- **Three narrowings, and they are not the same thing.** `Scopes` (status, key
  `f`) and `Periods` (issue date, key `t`) are request parameters and each
  costs a fetch; the text filter (`/`) narrows loaded rows and does not. They
  share a line but are labelled apart, or a user learns the wrong cost model.

  Status and period are separate axes because a user wants unpaid *and* this
  month — one combined list would need an entry per combination. Periods use
  the API's own time-filter constants (`sf values time-filters`) rather than a
  date range, which would need two more inputs to say what one constant says.
  "All time" sends `created:0` explicitly: the parameter is documented with a
  default of 6 (this year), so sending nothing leaves the window up to the
  server, and hiding older invoices is the failure worth avoiding.
- **The detail pane reads the row, not the API.**
- **The detail layout is shared with the CLI** (`render.DetailLines`), so
  `sf invoice view` and this pane cannot describe one record two ways. See
  [002 · CLI](002-cli.md).
- **Pages come from a 30s session cache.** See [004 · Caching](004-caching.md).

## The loading indicator

It goes **where the rows will be**, not on the status line — the eye is on the
region about to change, and a glyph on the last line of the terminal is not
where anyone is looking.

```
 ┌──────────────────────────────────┐   ┌──────────────────────────────────┐
 │ ID      NUMBER   CLIENT          │   │ ID      NUMBER   CLIENT          │
 │──────────────────────────────────│   │──────────────────────────────────│
 │                                  │   │ 309127  2026006  Acme s.r.o.     │
 │         ⣾  Loading invoices…     │──►│ 309128  2026007  Beta a.s.       │
 │                                  │   │ 309129  2026008  Gamma s.r.o.    │
 └──────────────────────────────────┘   └──────────────────────────────────┘
   columns stay — they belong to          same geometry, nothing moves
   the resource, not the response
```

The columns are drawn during the fetch, at the widths the resource measured on
its **last** load (`rememberWidths`). Widths come from the rows, so with none
loaded they render cramped and jump sideways a frame later — that jump, not the
brevity of the spinner, is what read as flicker.

No artificial delay and no minimum duration: a browser whose whole argument is
speed should not be made to feel slower to prove it was working.

While a fetch is in flight nothing claims the account is empty — "Nothing here."
and "No records." are statements about the account, not about a pending request.

## The open record

`enter` hides the table and gives the screen to one record. It is a mode of its
own, so while it is open:

- **tabs are locked.** Switching underneath would swap the account out from
  behind a detail that still looked like the old one, and the way back — `esc`
  — is right there.
- **the key bar drops what it cannot do.** No navigate, no filter, no expand;
  `esc back · ctrl+u/d scroll · q quit`.

### Keys

Actions are dispatched **before** the browser's own paging, for everything
outside `reservedKeys`. Paging answers to `n` and `p` as well as the arrows, and
those cases used to return first — so an action bound to either letter was
swallowed. `p` for payment worked only because somebody had noticed and added a
special case; `n` for create was unreachable from the keyboard while looking
perfectly wired. One rule instead of a special case per collision, and a test
that fires an action on each of the two letters.

`reservedKeys` is the other half: navigation, `enter`, `esc`, `q`, `tab`, and
the three narrowings `f`, `t`, `/`. An action cannot take those over.

### Acting on part of a record

`i` adds a line item to the highlighted document. It is the same
`sf invoice item add` the CLI runs, so the field carries its validator and its
running total.

Two things make it work, and neither is obvious:

- **The parent id is not a field.** It is injected from the highlighted row on
  submit. A box showing it would be a value the user must not change, and
  `Prefill` cannot carry it either — a prefilled value left alone is
  deliberately dropped, so the id would vanish on the way out.
- **One rich field still opens a form.** The count is no longer the whole rule:
  a single field carrying a validator, a note, options, or marked required gets
  the form anyway, because the inline footer prompt has nowhere to show any of
  them. Suppressing the parent flag left exactly one field, and the line-item
  box would have lost its parser and its total to a bare text input.

The key bar lists a resource's own actions **before** navigation, since it
truncates at the terminal width and what should survive is what a user cannot
guess: arrows scroll and enter opens in every terminal program ever written,
but nothing suggests that `i` adds a line item.

**`r refresh` and `q quit` are pinned to the end**, and their width comes off
the budget before anything competes for it. Reordering without that reservation
pushed both off an 80-column terminal — the commonest width there is — and
neither appears anywhere else on screen: nothing polls, so `r` is the only route
to fresh data, and the freshness band says how old the screen is without saying
how to change it. The ellipsis is reserved too, or the one mark that says
"there is more" is itself what gets clipped.

Deleting an item is CLI-only. The ids are on screen in the detail pane's item
table, so `sf invoice item delete <id> --invoice <id>` is a copy away, and a
second key that asks "which of these" needs a nested cursor the browser does not
have.

### Creating a document

An expense and a client could always be created here; an invoice could not, and
the only reason was its line items. They are typed one per line, in the same
`name:quantity:unit_price:tax` syntax the CLI's `--item` takes and its parser
already covers.

```
   Line items
   2 items · 640.00 + 147.20 VAT = 787.20     ← recomputed as you type
   Konzultácie:8:75:23
   Cestovné:1:40:23
```

Each line is parsed as it is entered, so an unusable one is named by its number
while the cursor is still in the box rather than coming back as a server error.
The total is the arithmetic the server will do, done twice — a figure that is
not the one you expected is worth seeing before the invoice exists. When a line
will not parse the total steps aside rather than showing a number built from
input the validator is already objecting to.

The compromise is honest: this is a syntax, not four fields. What it buys is
that the whole list is visible at once and any line can be corrected, which a
group asked once per item cannot offer. Expenses take the same `--item`, and on `add` alone: `/expenses/edit` appends
line items exactly as `/invoices/edit` does, so the browser's edit form must not
offer the box at all — it would have shown an empty "Line items" field on an
*edit* form, which is the most misleading way to present an append.
`sf invoice item add` and `sf expense item add` are where the append lives.

## Questions, prompts and failures

The failure is shown against the row it was about, not only in the key bar —
"Data validation error" at the bottom of the screen leaves the reader to work
out which record it referred to, and after an edit there is exactly one.

```
 │ 4505  2026002  TEST                    2026-08-01  10.00    │
 │▓4504▓▓2026001▓▓sf-cli▓test▓—▓hosting▓▓▓2026-08-01▓▓49.00▓▓▓▓│  ← the row
 │ Delete expense 2026001? (y/n)                               │  ← right here
 │ 4503  2026000  Domain renewal          2026-07-30  12.00    │
```

**Inside the table, immediately under the highlighted row** — the same place a
failed write and a single-value prompt appear. The list is padded to a fixed
height, so at the foot of that block a question could be twenty blank lines
from the record it names, and answering "Delete expense 2026002?" meant looking
back up to check which row was highlighted.

The rows below shift down by as many lines as the notice takes, so the frame
still comes to exactly the terminal height. Long messages — the API joins
several field errors into one sentence — wrap and cap at three lines. With no
rows at all (an empty account, a standalone create) there is no row to sit
under, and it falls back above the detail pane.

A failure clears on `esc` and on any cursor move, since it describes one record
and would otherwise sit against a different one.

## Forms

Forms are **the CLI commands driven by hand**: fields come from the command's
own flags, and the write goes through its `RunE` with output diverted to a
buffer. A hand-written form per resource would be more code that starts correct
and drifts. Flag variables are package-level, so `runCommandWithValues` resets
them afterwards or the next invocation inherits them.

```
   press e
      │
      ▼
   Action.Prefill(row) ──► {"name":"TEST UI", "due":"2026-08-15"}
      │                     raw API values, never the rendered column
      ▼
   ┌─────────────────────────────┐
   │ Invoice name                │   formInitial[] remembers what
   │ > TEST UI                   │   each box opened with
   │ Due date (YYYY-MM-DD)       │
   │ > 2026-08-15                │
   │ Send?                       │
   │   [ Send ]   Cancel         │   ← starts on Send; esc abandons
   └──────────────┬──────────────┘
                  ▼
        value != initial && value != ""
                  │
          ┌───────┴────────┐
          ▼                ▼
       send it         skip it
                  │
                  ▼
        nothing changed → "Nothing to send", no write
```

**Labels are the flag's help, cut short.** The part before the first bracket or
comma is the name somebody already wrote for the field — "Issue date",
"Constant symbol", "Document type" — and the rest goes inside the empty box as
a placeholder. The whole help string as a label read as prose: "Existing
client, by numeric ID or by name" above a box is a sentence, and fourteen of
them stacked is what made the form a wall. A head with no separator and too
long to be a label falls back to the flag's own name.

**A required field is marked and holds the form.** The asterisk is accented on
its own so the label keeps the weight every other label has, and it survives a
terminal with no colour. `requiredFields` is the API's own requirement restated
for a form with no `--data` to stand in for it — an invoice needs a client and
something to bill for.

```
   Existing client *
   required                 ← under the label, not at the foot of the form
   > — choose one —
     Acme s.r.o.
```

The complaint goes in the field's **description**, which is the only slot huh
gives a field next to itself; its own footer is switched off rather than saying
it twice. That costs a line per validated field even when nothing is wrong —
huh reserves the description whether it renders anything or not, five lines on
the invoice create form. The price of every complaint being where its field is.

**A form that cannot be completed is not opened.** A required list with nothing
in it — an invoice on an account with no clients — is refused with the reason
instead of being filled in and rejected. The select would otherwise offer only
its own "choose one" placeholder and there is nothing the form could do about
it.

Editing requires nothing. An untouched edit form is a no-op by design, so
compulsory fields there would only be in the way.

Date fields are validated in the form, so a bad date is caught under the field
being typed into rather than coming back from the server as something else. The
rule is narrow on purpose — see [001 · API integration](001-api-integration.md).
They also prefill without the time the API attaches to them: it returns
`2026-08-02 00:00:00` for a field it documents as `YYYY-MM-DD`, and in a box
labelled for the date alone the rest is something to delete before typing.

**A flag whose value comes from a fixed set is a list, not a box.**

```
   Document type
   ▸ regular invoice        ← a select: arrow through it
     proforma invoice

   Tags
     [✓] sf-cli test        ← a checklist: a record can carry several
     [ ] urgent

     [ Update ]  Cancel     ← named for what it does, not "Send"
```

Mostly the lists carried as constants (`invoice-types`, `expense-types`,
`payment-types`, `delivery-types`, `languages`, `rounding-types`), which cost
nothing. **Tags are the exception**: a repeatable flag, so a checklist, and the
only list read from the API. It is worth the request because the API takes only
numeric ids and drops a tag name without a word — ticking names is the
difference between saving a tag and thinking you did.

`FormField.Options` is a function for that reason: it is called when the form
opens, not when the browser starts, or every session would spend a request on a
dropdown most of them never draw. Expense categories, sequences and countries
are still left out — they have no second reason to pay for.

Two rules keep a list from writing something nobody chose:

- **A value the list does not name is kept as an option.** Without it a record
  carrying an unknown type would land on the first choice, and confirming would
  write a change nobody asked for. An unset field is the same problem with an
  empty value, and gets `— not set —`.
- **No `Height` on a select.** Setting one makes huh recompute the viewport
  with `YOffset = selected`, which pins the highlighted option to the top and
  scrolls the list underneath a stationary arrow — the cursor stops being a
  cursor. Unset, the viewport is sized to the whole list and the arrow moves
  down it. A long list costs length, and the form already scrolls.
- **Search needs nothing enabled.** `/` inside a focused select starts filtering
  by itself. `Filtering(true)` does not switch that on — it starts the field
  *already* filtering, which is why an earlier attempt at it left a bare `/`
  where every label should have been. The client roster is the field it matters
  for: the account's clients, searchable, costing the one request that typing a
  name already spends on `resolveClient`.
- **A validator has to reach the field whatever shape it took.** Only
  `huh.Input` was being given one, so a required *select* was unenforced — the
  client on the create form could be left empty and the write went out to be
  refused by the server instead. Selects and checklists take it now.
- **A repeatable flag with nothing to tick is a box of one value per line.**
  That is how line items are entered — huh has no repeating group, and a line
  item is four values, so no single field fits one. See below.
- **A checklist needs no such guard.** A value the list does not name is simply
  not offered, and leaving the boxes alone sends back the same set, which the
  change check then discards.

Multi-valued fields travel through the shared `map[string]string` joined by
newlines, and `runCommandWithValues` calls `Set` once per value — pflag's
`stringArray` splits nothing, so one call would make a single tag with a
newline in its name. A comma would have been the obvious separator and can
appear in a tag name.

`--type` means a different set on each resource, so it is resolved from the
command rather than the flag name — the one place the flag name is not enough.

**Only changed fields are sent.** Submitting every box would write back fields
nobody looked at, and a value shown one way is not always the value that should
be written — a round trip through the form could rewrite a record by merely
being opened.

`prefillFrom` maps a flag to its field by convention (the flag name with dashes
for underscores), with `fieldPaths` covering the few flags named for what they
mean rather than for the field they set. An unresolved mapping costs an empty
box, never a wrong one.

One field prompts inline in the footer; several open a form. The count is the
whole rule.

## Notes

- The request spinner is switched off before the browser starts — both would be
  drawing at once.
- Read-only mode hides write actions entirely rather than refusing them when
  pressed, so the mode is visible instead of a surprise. There is no flag of
  its own — `sf ui --dry-run` turns it on, because the client is already
  refusing writes at that point. *A dedicated `--read-only` would be clearer
  than borrowing the dry-run flag; it has not been added.*
- Destructive actions always confirm. These records are somebody's accounting.
